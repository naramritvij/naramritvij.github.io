CivicFlow AI

commit 4e91a2c · FastAPI · Oracle DB · Gemini · React

The problem

Civic and municipal incident reports — potholes, outages, service complaints — tend to land in whatever channel is easiest for the reporter (a form, an email, a call log), which leaves staff manually reading, categorizing, and routing each one before anything gets fixed. That manual triage step is where response time gets lost.

What I built

CivicFlow AI is a full-stack incident intelligence system: a FastAPI backend persists reports to an Oracle database, Google Gemini reads each incoming report and assigns a category, urgency level, and a short summary, and a React front end gives staff a live queue to review, filter, and close cases from.

Design decisions

  • Oracle as the backbone — chosen over a lighter store because the course context and downstream reporting needs called for relational integrity: foreign keys tying reports to categories, staff, and status history.
  • LLM in the loop, not the driver — Gemini classifies and summarizes, but every categorization is editable by a human reviewer before it's final. The model speeds up triage; it doesn't replace the judgment call.
  • API-first backend — FastAPI exposes clean endpoints for ingest, review, and status updates, so the React app is a thin client rather than where any business logic lives.

What it improved

The categorize-and-summarize step that used to require a person reading the full report now happens the moment it's submitted, so staff open a queue that's already sorted by urgency instead of a raw inbox.
