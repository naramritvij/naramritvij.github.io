TTC Service Disruption & Passenger Impact DB

commit 9b0f6d1 · Oracle SQL · Data Modeling · ERD

The problem

Transit disruptions — delays, closures, diversions — and their impact on riders are usually tracked in scattered, flat records that make it hard to answer relational questions: which routes get hit hardest, how disruption type correlates with passenger complaints, how impact trends over time.

What I built

A normalized Oracle database purpose-built for TTC-style disruption data: entities for routes, stations, disruption events, causes, and passenger impact reports, connected through a crow's-foot ERD and enforced with real constraints rather than left to application code.

What's in the build

  • Full DDL/DML — schema creation scripts and seed data covering routes, events, and impact records.
  • Views for the recurring analytical questions — worst-affected routes, disruption frequency by cause, month-over-month impact trends — so they're one query away instead of re-derived each time.
  • Triggers enforcing referential and status-consistency rules that would otherwise depend on the application layer behaving correctly every time.
  • Crow's-foot ERD documenting cardinality decisions before a line of DDL was written.

Why relational, not just a spreadsheet

The value of this dataset is in the joins — a disruption is only useful once it's tied to the route, the time window, and the passengers it affected. A relational schema with enforced keys makes those joins reliable instead of hopeful.
