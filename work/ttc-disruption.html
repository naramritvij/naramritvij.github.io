TTC Service Disruption System

A role-based transit operations platform with developer and passenger experiences, custom Node.js HTTP routing, Oracle-backed disruption data, audit logging, restore flows, response coordination, and passenger notifications.

01 / overview

Model transit disruption operations as a system, not a single CRUD screen.

The platform separates operational and passenger-facing concerns. Developers manage disruption records, response coordination, audit history, and recovery, while passengers see a simplified notification feed backed by the same relational data.

01Two user experiences

Developer/Admin operations and Passenger-facing notification views.

02Auditability

Soft-deleted disruption records are logged and can be restored through the application.

03Relational operations

Lines, stations, routes, causes, severities, statuses, teams, and disruptions are connected in Oracle.

02 / architecture

Role-aware frontend over a custom API and relational backend.

A React interface talks to a Node.js server built on the native HTTP module. Oracle stores operational entities, audit records, and passenger-facing views.

system_viewarchitecture / data flow

Role-specific screens share the same backend and relational model, while database audit and notification structures support very different workflows.

03 / flow

Operational disruption lifecycle

The design supports the full record lifecycle instead of treating deletion as irreversible.

01Authenticate

Role determines access to developer operations or passenger views.

02Create / update

Developer dashboard manages disruptions and related operational data.

03Coordinate

Response-team and shift information supports incident handling.

04Audit

Soft deletes are written to deletion audit history.

05Restore / notify

Records can be restored; passengers consume the notification view.

04 / access model

Different roles see different operational surfaces.

The system keeps internal disruption-management capabilities separate from the simplified passenger notification experience.

05 / decisions

Key engineering decisions

  • Custom native-HTTP backend - routing was implemented without Express, making request parsing and route behavior explicit.
  • Named Oracle bind parameters - queries use bind variables instead of interpolating user input.
  • Soft delete with recovery - deletion preserves an audit trail and supports restore instead of permanently destroying operational history.
  • Role-specific UX - passengers are not exposed to developer operations, while operational users get richer CRUD and coordination tools.
