01 / overview

A realtime game designed to run without a server to babysit.

Students scan a QR code, make Home / Draw / Away predictions before kickoff, and see points and streaks update after full time. The operational requirement was as important as the interface: it needed to keep running even when the development laptop was offline.

0172 group-stage fixtures

The experience includes the complete official group-stage fixture set.

02Realtime state

Firestore listeners synchronize predictions, results, and leaderboard state across devices.

03Automated results

A scheduled Node.js job checks finished matches and writes winners without manual entry.

02 / architecture

Static frontend, realtime database, scheduled automation.

The browser application handles interaction and realtime state. Result ingestion is separated into a small scheduled automation path.

system_viewarchitecture / data flow

The application path and result-ingestion path are deliberately decoupled: participants interact with a static app, while scheduled automation updates authoritative match results.

07 / decisions

Key engineering decisions

  • Static app instead of a permanent server - the interaction layer stays simple to deploy and avoids maintaining an always-on application backend.
  • Firestore for synchronization - realtime listeners keep phones and public screens aligned without custom websocket infrastructure.
  • GitHub Actions as scheduled backend work - a cron-triggered Node.js job handles result ingestion while preserving the lightweight hosting model.
  • Quota-aware API calls - the bot requests football data only when a match is actually waiting for a result.
scoring model

Ranking prioritizes total correct picks, then best streak, then accuracy. A skipped match does not break the current streak; an incorrect prediction does.
